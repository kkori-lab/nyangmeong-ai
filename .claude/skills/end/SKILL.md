# 세션 마무리

`<이름>`은 브랜치 이름이다(`/`가 있으면 앞부분). 기억이 아니라 명령 출력을 근거로 쓴다.

0. `sh scripts/end-check.sh`를 돌린다(이 세션에 검증 보고가 있으면 `--no-build`). 검증 명령(1번), 한 일(3번), 검증 루프 보관(4번), 핸드오프 줄 수와 개인 경로·비밀값 의심, 스킬 동기화(6번), 커밋 종류와 푸시·PR 상태(7번)를 모아 준다. 같은 명령을 손으로 다시 돌리지 않는다.
1. 검증: 이 세션의 마지막 검증 보고(`/impl` 또는 `/verify`)의 판정을 쓴다. 없으면 end-check의 "## 검증 명령"을 쓴다. 명령이 0이 아니거나 판정이 `실패`면 작업은 끝나지 않았다. 검증 보고가 없고 기획의 기능 ID 중 아직 만들지 않은 것이 있어도 끝나지 않았다. `확인 못 함 있음`이면 5번 기준으로 본다.
   - 끝나지 않았으면 중간 저장이다. 2번을 건너뛰고 3번부터 이어 간다. 마일스톤은 `진행`으로 두고, 보고에 끝나지 않은 이유(실패한 명령·판정, 만들지 않은 기능 ID)를 적는다.
2. 사람 확인: 사람이 확인했다고 답한 적이 없으면 확인 목록을 보여 주고 멈춘다. 환경(`.env.local`, 남의 API·백엔드 서버)이 없어 확인할 수 없어 보여도 대신 판단하지 않고 묻는다. README를 보라고만 하지 않는다.
   - `### 추가 요청`이 있으면 그 줄을 따로 보여 주고, 직접 요청한 것이 맞는지도 함께 확인받는다. 요청하지 않았다는 줄은 되돌릴지 묻는다.
   - 검증 보고의 "사람 확인"을 그대로 옮긴다. 없거나 빠진 기능 ID는 기획과 코드로 같은 형식으로 만든다.
   - 띄울 명령(어느 저장소에서), 브라우저에 붙여 넣을 전체 URL, 할 동작 → 기대 결과가 있어야 한다.
   - 끝에 "확인했으면 `확인`, 문제가 있으면 그 내용을 답해 주세요". `확인`이면 3번부터 이어 간다.
   - 문제나 추가 요청을 답하면 여기서 코드를 고치지 않는다. "`/impl`로 이어 가세요. 추가 요청으로 기록하고 고친 뒤 다시 검증합니다"라고 하고 멈춘다.
3. 한 일은 end-check의 "## 한 일"이다.
4. end-check의 "## 검증 루프"로 잠금을 본다. 잠금이 있었으면 스크립트가 `pause`로 보관했다. 회차와 실패 항목을 핸드오프 "다음에 할 것"에 옮긴다. 보관은 지우는 것이 아니다. 다음 세션의 첫 검증에서 같은 회차·같은 기준 파일로 되살아나고, 보관 중에는 핸드오프·마일스톤만 고칠 수 있다. `clear`는 여기서 부르지 않는다(5번에서 `끝`으로 판정된 뒤에만 부른다). 그다음 `handoff/<이름>.md`를 고친다.
   - "지금 하는 것": 끝남 또는 진행 중, 한 줄 설명.
   - "다음에 할 것": 남은 일. 실패한 명령, 검증 루프 회차와 실패 항목, 사람이 답한 문제는 맨 위. 마일스톤이 `진행`이라 검증 루프를 보관해 둘 때만 "검증 루프 <N>회차 실패로 보관 중. 기획은 고치지 않는다. 루프를 버리려면 `! sh scripts/verify-loop.sh clear`"를 함께 적는다. 기획(기능 ID·완료 조건·새 의존성)은 고치지 않는다.
   - 60줄을 넘으면(end-check "## 핸드오프") 끝난 항목을 지우고 보고에 적는다. "개인 경로·비밀값 의심"에 줄이 나오면 그 줄을 고친다.
5. 마일스톤 `끝` 판정은 여기서만 한다. 아래를 모두 만족하면 `sh scripts/milestone-status.sh <SCR-ID> 끝`, 아니면 `진행`으로 둔다(같은 화면 ID의 절이 여럿이면 세 번째 인자로 제목에 든 글자). 판정과 근거(못 맞춘 항목)를 보고에 적는다.
   - 검증 명령이 모두 0이고 판정이 `실패`가 아니다.
   - 마일스톤의 기능 ID와 추가 요청이 모두 셋 중 하나다: 검증 보고에서 통과, `연결 남음`, 기획에서 다른 마일스톤으로 넘김.
   - 검증 보고의 "확인 못 함(내 것)"이 없다.
   - 사람이 `확인`이라고 답했다(2번).
   - `끝`이면 그 마일스톤 절에 `- 연결 남음: <기능 ID> (<기다리는 것>, <담당>)`을 남기고, 같은 항목을 핸드오프 "다음에 할 것"에 올린다.
   - `끝`이고 보관한 잠금(4번에서 보관했거나 검증이 통과 뒤 보관한 것)이 있으면 `sh scripts/verify-loop.sh clear`로 버린다. `끝`은 사람 확인(2번)을 거친 판정이라 그 확인에 루프를 버리는 것도 포함한다. 핸드오프에 "보관 중" 문구를 이미 적었다면 지운다. `진행`이면 버리지 않고 보관한 채 둔다.
6. end-check의 "## 스킬 동기화"가 `차이 없음`이어야 한다(스크립트가 `.claude/skills/`를 `.agents/skills/`로 복사하고 비교했다). 4·5번에서 스킬을 고쳤으면 `sh scripts/end-check.sh --no-build`를 다시 돌린다.
7. 커밋 메시지를 제안한다(`docs/convention/git.md` 형식). 종류는 들어가는 변경으로 정한다(end-check "## 커밋 종류").
   - 코드가 있으면 코드·핸드오프·마일스톤을 한 커밋으로. 제목 `[이니셜] feat: <화면 ID> <이번에 만든 것>`(버그 수정만이면 `fix`). 화면명이 아니라 실제로 만든 것을 쓴다.
   - 본문: 진행 중이면 첫 줄에 "진행 중"과 남은 것. 기능 ID별 한 줄. 추가 요청이 있으면 `추가 요청:` 아래에 한 줄씩. 남에게 영향이 있으면 "영향:" 줄(새 환경변수·설정 변경, 추가한 라이브러리, 공유 파일, 남과 맞출 결정).
   - `handoff/`·`milestones/`만 바뀌었으면 `[이니셜] docs: 핸드오프 갱신`.
   - `.claude/skills/`·`.agents/skills/`·`scripts/` 변경이 섞여 있으면 "공용 하네스 변경이 섞여 있습니다. PR로 따로 올리세요"라고 알리고 커밋에서 뺀다. 6번 동기화로 생긴 변경도 같다.
   - `Co-Authored-By:` 같은 AI 도구 줄은 넣지 않는다. 사람이 `커밋`이라고 답하면 커밋한다.
   - 커밋한 뒤 푸시를 제안한다: 올릴 커밋 목록(`git log origin/<이름>..HEAD --oneline`, 커밋 전이면 end-check "## 푸시·PR")을 보여 주고 "푸시하려면 `푸시`라고 답해 주세요". 답하면 `git push origin <이름>`만 한다. `develop`·`main`에는 푸시하지 않는다.
   - 푸시한 뒤 PR: 열린 PR(end-check "## 푸시·PR")이 있으면 "이 커밋은 열린 PR #N에 들어갑니다"라고만 알린다. 없고 이번 마일스톤이 `끝`이면 "PR을 만들려면 `PR`이라고 답해 주세요"라고 묻는다(`진행`이면 묻지 않는다).
   - `PR`이라고 답하면: `sh scripts/pr-prep.sh`를 돌린다(`origin/develop` merge → 검증 명령 → 푸시). 종료 코드 4면 출력의 커밋하지 않은 파일 목록을 보여 주고 "이 파일들은 커밋하지 않은 채로 두고 진행할까요? 검증 명령에는 이 변경도 포함됩니다. 진행하려면 `진행`이라고 답해 주세요"라고 묻고 멈춘다. `진행`이면 `sh scripts/pr-prep.sh --allow-dirty`로 다시 돌린다. 그 밖에 0이 아니면 출력(충돌 파일·실패 줄)을 그대로 보여 주고 멈춘다. 충돌은 스크립트가 abort 하지 않고 그대로 둔다. 0이면 `gh pr create --base develop --head <이름>`. 제목은 커밋 형식이다. 본문은 `.github/pull_request_template.md`를 읽어 섹션 제목·순서를 그대로 채운다(규칙은 `docs/convention/git.md` "PR"). 해당 없는 섹션은 `없음`이라고 쓴다. `Features` 표는 마일스톤의 기능 ID와 검증 보고로, `Test Plan`의 `Result:`는 검증 판정과 회차로, 호출 체크박스는 사람 확인으로 채운다. `Design Decisions`는 기획과 달라진 것과 다른 담당에 영향 가는 선택만 쓴다. AI 도구 문구는 넣지 않는다. `gh`가 없으면 `https://github.com/<저장소>/compare/develop...<이름>` 주소와 본문을 보여 준다.
   - 병합은 하지 않는다. 사람이 GitHub에서 한다.
8. 보고: 검증 명령별 종료 코드, 사람 확인 결과, 바뀐 절, 동기화 결과, 확인 못 한 것. 마지막 줄:
   - 끝났으면 "다음 작업은 `/clear` 한 뒤 `/start`로 시작하세요"
   - 아니면 "이 작업은 끝나지 않았습니다. `/clear` 한 뒤 `/start`로 이어 가세요"

핸드오프는 공개 저장소에 커밋된다. 비밀값과 개인 PC 경로를 적지 않는다.

# 구현 검증

구현한 대화를 보지 않고 저장소만 보고 판정한다. 보고는 처음부터 끝까지 한국어로 쓴다. 파일을 고치지 않고 고칠 곳은 보고만 한다(검증 루프 잠금은 `scripts/verify-loop.sh`로만 남긴다). 변경은 diff로 확인하고 추측하지 않는다.

1. `sh scripts/verify-collect.sh`를 돌린다. 1~4번에 쓸 사실(기획, 바뀐 것, 검증 명령 종료 코드, 기획 밖 변경 후보, 새 의존성, 기준 변경)을 모아 준다. 같은 명령을 손으로 다시 돌리지 않는다. 종료 코드 3이면 "기획 없음"이라고 하고 멈춘다.
   - "## 기획"은 `handoff/<이름>.md`의 "지금 하는 것"이다. 기획, 시작 시각, `### 추가 요청` 절을 여기서 읽는다. 추가 요청 줄은 기획의 기능 ID와 똑같이 다룬다(기능 ID는 `추가-<번호>`).
2. 바뀐 것: 출력의 "## 바뀐 것". 내용은 `git diff`로 확인하고 추측하지 않는다.
3. 검증 명령: 출력의 "## 검증 명령"(AGENTS.md의 검증 명령과 같다)의 종료 코드와 실패 줄을 적는다.
4. 기획과 대조한다.
   - 기능 ID마다 구현한 변경이 있는가.
   - 기획과 추가 요청에 없는 파일이 바뀌었는가. 출력의 "기획 밖 변경 후보"는 기획에 경로·파일 이름이 적히지 않은 파일이다. 그중 기획한 클래스를 받치는 보조 파일(설정 값 클래스 등)과 그 테스트는 세지 않고 비고에만 적는다. `handoff/`·`milestones/`도 세지 않는다.
   - "## 새 의존성"에 `새 의존성:`에 없는 라이브러리가 들어왔으면 기획 밖 변경이다.
   - "## 기준 변경"(`verify-loop.sh check`)에 파일이 나오면 첫 실패 뒤 기준 파일(기획·검증 명령·의존성·테스트)이 바뀐 것이다. `기준 변경:`에 적는다.
     - `handoff/`·`milestones/`는 진행 기록도 바뀌므로 함께 나온 `git diff --no-index` 명령으로 첫 실패 때 사본과 비교한다. 기획(기능 ID·완료 조건·새 의존성·검증 명령)이나 마일스톤의 기능 ID가 바뀌거나 빠졌을 때만 기준 변경이다. 진행 상태·시각·"다음에 할 것"·회차 기록은 세지 않는다.
5. `화면:` 완료 조건은 AGENTS.md의 방법으로 확인한다. 못 하면 이유를 적고 둘 중 하나로 나눈다.
   - `연결 남음`: 기다리는 것이 `milestones/<이름>.md`의 그 마일스톤 "API가 남의 것"·"기다리는 것"에 있거나, `docs/convention/milestone.md` 담당 표에서 남의 화면·라우트일 때만. 기다리는 것과 담당을 적는다.
   - `내 것`: 그 밖 전부(가짜 값을 바꿀 수 없음, 이 마일스톤 코드의 빠진 부분 등). 확인할 수 있게 하는 방법을 적는다.
6. 판정이 `실패`면 `sh scripts/verify-loop.sh fail "<실패 항목 한 줄>"`을 돌려 나온 회차를 적는다. 아니면 `sh scripts/verify-loop.sh pause`(잠금을 보관만 한다. 버리는 `clear`는 부르지 않는다. `/end`가 `끝`으로 판정할 때 버린다).
7. 보고한다.

```
검증 명령: <명령> → <종료 코드> (실패 줄)
기획 밖 변경: <파일> 또는 없음
기준 변경: <파일> 또는 없음
| 기능 ID | 변경 있음 | 명령 | 화면 | 비고 |
확인 못 함(내 것): <기능 ID> <이유> → <확인할 수 있게 하는 방법> 또는 없음
연결 남음: <기능 ID> (<기다리는 것>, <담당>) 또는 없음
판정: 통과 / 실패 / 확인 못 함 있음
회차: <verify-loop.sh 출력> (실패일 때만)

사람 확인:
- 띄우기: <명령>(어느 저장소에서)
- <기능 ID>: <전체 URL 또는 API 메서드·경로> → <할 동작·넣을 값> → <기대 결과>
- 테스트로만 확인할 것: <조건> → `<테스트 명령>`
- 정리: <확인용 데이터 지우는 방법> 또는 없음
- 바뀐 파일: <목록>
```

- 판정은 하나만 고른다. 검증 명령이 0이 아니거나, 변경 없는 기능 ID가 있거나, 기획 밖 변경이나 기준 변경이 있거나, 확인 못 함(내 것)이 있으면 `실패`(내 것은 고칠 곳에 "확인할 수 있게 하는 방법"을 적는다). 그렇지 않고 연결 남음이 있으면 `확인 못 함 있음`. 둘 다 아니면 `통과`.
- "사람 확인"은 판정과 관계없이, 사람이 그대로 따라 할 수 있게 쓴다. 기능 ID는 기획에 적힌 짝을 그대로 쓴다. 값은 코드에서 확인한 실제 값이다(README "사람 확인" 참고).
  - 띄우기는 `uv run uvicorn app.main:app --reload`(이 저장소)이고, 확인할 `AI_MODE`(mock·real)를 함께 적는다. real이 필요하면 필요한 `.env.local` 키 이름을 적는다(값은 적지 않는다).
  - AI 대화창(`/ai/**`): Postman으로 보낼 요청. 메서드와 전체 URL(`http://localhost:8000/ai/...`), Headers, Body(raw JSON), 기대 응답 코드와 JSON. 스트리밍 응답은 받을 이벤트 순서를 적는다. 상태를 바꾸는 요청은 Headers에 `X-Requested-With: XMLHttpRequest`를 적는다. 로그인이 필요하면 첫 줄에 백엔드 저장소에서 `./gradlew bootRun`을 띄우고 `POST http://localhost:8080/api/auth/dev-tokens`(Headers `X-Requested-With: XMLHttpRequest`, Body `{"mbrSn": <번호>}`)로 쿠키를 받는 단계를 적는다. 쿠키는 포트와 관계없이 `localhost`에 붙으므로 8000 요청에도 실린다.
  - 내부 API(`/internal/v1/**`, Java만 부른다): 키 헤더는 없다. 파일을 보내는 요청은 Body form-data와 필드 이름을 적는다.
  - 만료 토큰·외부 API 시간 초과처럼 Postman으로 만들기 어려운 조건은 그 테스트와 `uv run pytest <파일>::<테스트 이름>`. 참고로 API 문서(`http://localhost:8000/docs`)에서 찾을 API 이름도 적는다.
- 마지막 줄:
  - 통과: "위 '사람 확인'대로 확인한 뒤 `/end`로 마무리하세요"
  - 실패: "고칠 곳을 고친 뒤 `/verify`를 다시 실행하세요"
  - 확인 못 함 있음: "남은 것은 연결 남음뿐입니다. 위 '사람 확인'대로 확인한 뒤 `/end`(끝 여부는 `/end`가 정합니다)"

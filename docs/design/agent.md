# AI 매니저 에이전트 루프 설계 (초안)

2026-11-26, LJS. 마일스톤 "SCR-AIM-004 대화창 · AI 매니저 에이전트 ① 설계·계약 초안". 이 문서는 설계와 결정 남음만 다루고 코드는 ②부터 바꾼다.
React 계약 초안은 `docs/api/chat.md`의 "(에이전트 초안, 2026-11-26, 프론트 합의 전)" 표시가 붙은 행·절이다. 프론트와 합의하기 전에는 구현하지 않는다(AGENTS.md 4번).
도구 목록·카드 모양은 `tool-catalog.md`, 도구 고르기·평가 기록은 `tool-calling.md`를 따른다.

## 0. 한 줄 요약

회원 메시지 하나(한 턴) 안에서 **읽기 → 쓰기 → 결과 보기 → 다음 행동**을 LLM이 이어 가고, 언제 끝낼지도 LLM이 정한다.
쓰기는 지금처럼 React가 확인 카드의 `call`로 Java 공개 API를 실행하고, Python은 상태 없이 멈춘 루프를 서명 토큰에 실어 React에 맡긴다.
서버 규칙(빈 칸·같은 이름 반려동물·삭제 동사·번호 칸·소유 검사)은 지금 코드 그대로 루프의 모든 단계에 걸린다. 백엔드 변경은 없다.

## 1. 지금 흐름과 바뀌는 곳

지금 한 턴(`app/chat/service.py`):

1. 도구 고르기 LLM이 도구를 고른다(`judge_tools`).
2. 읽기 도구면 Python이 Java 읽기 API를 부르고, 결과를 본 LLM이 답을 쓰면서 도구를 더 고를 수 있다(`_Follow`). 읽기는 한 턴 `READ_LIMIT`(3)번, 쓰기 카드는 한 번 고르면 끝(카드 최대 `ACTION_MAX_CARDS` 3장).
3. 쓰기 카드면 `done.action(s)`로 주고 턴이 끝난다. 동사형 명령이면 `done.execute: true`(2026-11-26).
4. React가 카드를 실행하고 `action-result`를 부르면 Python은 결과 글만 저장한다(`save_action_result`). LLM은 실행 결과를 보지 못한다.

그래서 "탄이 체중 기록하고 지난주보다 늘었는지 알려 줘"는 기록 카드에서 끝나고, 비교는 회원이 다시 물어야 한다. Java 400 칸 오류도 회원이 카드를 고쳐 다시 말해야 한다.

바뀌는 곳:

| 곳 | 지금 | 바뀜 |
| --- | --- | --- |
| `_Follow` | 읽기 3번·쓰기 카드 1번 | 한 턴 도구 상한(3절) 안에서 읽기·쓰기를 몇 번이든, 쓰기 카드가 나오면 루프를 멈춤. ②에서 구현됨(2026-11-26): 읽기 상한 `TOOL_LIMIT` 8번, 쓰기는 카드 1장에서 멈춤(여러 번 쓰기는 ③) |
| `_search_answer` | 첫 글자 10초·뒤 60초 | 단계별 시간 + 전체 상한(3절), 읽기 전 `step` 이벤트. ②에서 구현됨(2026-11-26) |
| `done` | 카드에서 끝 | 이어 갈 수 있으면 `pending`(서명 토큰, 4절) |
| `save_action_result` | 결과 글 저장 | 그대로(JSON). 이어 가기는 새 API `agent-continue`(SSE) |

## 2. 루프

```
회원 메시지 ─▶ /messages (SSE)
  LLM 도구 호출 ─┬─ READ  : step 이벤트 → Python이 Java 읽기 → 결과를 LLM에 → 다시 LLM
                 ├─ CARD  : 카드를 모음. 이 응답의 카드를 다 모으면 루프를 멈춤
                 └─ 글만  : 끝 (LLM이 끝을 정함)
  멈춤 ─▶ done {action(s), execute, pending{agentToken}}
React ─▶ 카드마다 call 실행 → action-result (지금 그대로)
      ─▶ pending이 있었으면 agent-continue {agentToken, results} (SSE)
  Python: 토큰 검사 → 결과(DONE·FAILED+errors·CANCELED)를 LLM에 → 위 루프를 이어 감
```

- 끝: LLM이 도구 없이 글로 답하면 끝이다. 그 글이 이 턴의 마지막 AI 메시지로 저장된다. 상한에 닿으면 Python이 더 부르지 않고 그때까지 결과로 답을 쓰게 한다.
- `pending`은 카드를 실행한 뒤 LLM이 할 일이 남았을 수 있을 때만 준다. 판단: 카드를 고른 LLM 응답에 같은 응답 안 다른 도구가 없고, 회원 문장이 카드만으로 끝나는 꼴(단순 명령 하나)이면 주지 않는다 — 지금 흐름과 같다. 판단 규칙은 ②에서 `rules`에 정하고 평가로 맞춘다.
- `CANCELED`면 이어 가지 않는다. React는 취소한 카드만 있으면 `agent-continue`를 부르지 않는다. 섞여 있으면 부르고 LLM은 취소한 일을 다시 하지 않는다.
- 사진 카드(`file` 칸)도 같은 길이다. React가 사진을 붙여 실행하고 결과만 돌려준다(저장은 React → Java, 2026-10-27 결정 유지).
- 무응답(회원이 실행·취소 어느 쪽도 하지 않음)이면 토큰은 만료로 버려진다. 다음 메시지는 지금처럼 새 턴이다.

## 3. 상한

| 상한 | 값 | 이유 |
| --- | --- | --- |
| 한 턴 도구 호출 | 8번 (읽기·쓰기 카드·이동·사용법 합쳐, 이어 가기 포함) | 단계당 약 2초(LLM 1.5~2초 + Java 읽기)라 8번이면 15~20초. 맴도는 루프를 끊는다. 루프 바퀴(LLM 호출)는 최대 8바퀴 + 답 쓰기 1번 |
| 첫 이벤트 | 10초 (`step`이나 `delta`) | 지금 "첫 글자 10초"를 루프에 맞게 |
| 단계당 LLM | 10초 (`LLM_TIMEOUT_SEC`) | 지금 값 |
| 전체 | 60초 (`answer_total_sec`, 이어 가기는 요청마다 따로) | 지금 값 |

- 쓰기 카드 수는 따로 세지 않는다(2026-11-26 사람 결정). 카드 한 장도 도구 호출 한 번이라 도구 상한이 카드 수도 막는다. 카드 만들기는 Python 칸 검사뿐이고 실행 부하는 지금 화면 저장과 같다(React → Java). 지금 계약의 카드 최대 3장(`ACTION_MAX_CARDS`, 요청 `actions` 4개 이상 400)은 ③에서 프론트와 합의해 8로 바꾼다(9절).
- 숫자는 한 곳 상수로 둔다(2026-11-26 사람 결정, 처음 값 8번). ②의 `tool_eval` 다단계 세트와 `turnlog`의 상한 걸림 턴(새 태그 `agent_limit`)을 보고 조정한다.
- 지금 `READ_LIMIT`(3)은 없애고 8번 안에서 센다(②에서 `TOOL_LIMIT`으로 바꿈). `PTC_CALL_LIMIT`(프로그래밍식 도구 호출 시험)은 따로 둔다.
- 전체 상한을 넘으면: 첫 글자 전이면 `error`, 글을 쓰는 중이면 지금처럼 미완료(`cmptnYn=false`)로 저장.

## 4. 서명 토큰 (`agentToken`)

Python은 상태를 갖지 않으므로(AGENTS.md 2번) 멈춘 루프를 React가 들고 있다가 돌려준다.

- 모양: `base64url(JSON 본문) + "." + base64url(HMAC-SHA256(본문))`. 표준 라이브러리 `hmac`·`hashlib`만 쓴다(새 의존성 없음).
- 키: 새 설정 키 `AGENT_STATE_KEY`(③에서 `.env.local.example`·디스코드 `.env.local`에 추가). 없으면 에이전트 이어 가기를 끄고 지금 흐름(`pending` 없음)으로 동작한다.
- 담는 것: `v`(형식 버전), `room`(`aiCnvrsRoomSn`), `exp`(만료, 발급 뒤 10분), `said`(원래 사용자 메시지), `messages`(LLM 메시지 기록: 도구 호출·READ 결과 글·카드), `left`(남은 도구 호출 수), `seen`(번호 칸에 쓸 수 있는 이 턴 READ 번호), `cards`(이 멈춤에서 낸 카드의 `tool`·`input`). ③ 구현(`app/chat/agentstate.py`): `messages` 대신 `q`(그 사용자 메시지 msgSeq)·`notes`(진행 기록 글 목록), 그리고 `done`(이 턴에서 실행이 끝난 카드, 반복 막기)·`fixed`(칸 오류를 고친 적 있음)를 담는다.
- 크기 상한 48KB(READ 결과 6000자 × 3 + 기록). 넘으면 `pending` 없이 지금 흐름으로 끝낸다.
- 검사(`agent-continue`): 서명 틀림·만료·`room`이 경로와 다름·`v` 다름이면 400 `INVALID_REQUEST`. `results`의 `tool`은 토큰 `cards`에 있는 것만 받는다.
- 암호화는 하지 않는다: 회원 본인 데이터가 HTTPS로 본인 브라우저에만 가고, 위조는 서명이 막는다. 다시 보내기(재생)는 막지 못하지만 쓰기는 늘 React 실행을 거치고 Java가 소유·중복을 검사하므로 읽기 비용만 든다. 대안은 9절.

## 5. 칸 오류 고치기

- `FAILED` + `errors`(Java 400 `data`의 `field`)가 오면 LLM에 칸 이름과 표시 이름을 주고 **한 번** 고친 카드를 받는다. `message`(Java 문구)는 LLM에 주지 않는다(지금 결과 글과 같은 이유).
- 고친 카드에 빈 칸이 없으면 동사형 명령과 같이 `execute: true`, 빈 칸이 생기면 지금처럼 되묻는다.
- 두 번째 실패나 `errors`가 빈 `FAILED`(가계부 서비스 검사 등)는 고치지 않고 지금 실패 글로 끝낸다.
- 고친 카드도 도구 8번에 센다.

## 6. 안전 규칙 (코드 그대로, 모든 단계에)

1. 빈 칸·같은 이름 반려동물이면 `execute` 없이 멈추고 되묻는다(지금 `action_ask_message`). 이때 `pending`도 준다 — 회원이 칸을 채운 다음 메시지는 새 턴이므로 토큰은 쓰지 않는다(③에서 다음 메시지에 토큰을 실을지 정함, 9절).
2. 삭제 카드는 회원 말(원래 메시지나 확인 말)에 삭제 동사가 있을 때만 `execute`. 루프가 스스로 고른 삭제는 확인 카드로 멈춘다.
3. 번호 칸(`…Sn`)은 이 턴(이어 가기 포함, 토큰 `seen`) READ 결과 값만 쓴다.
4. 회원 문장에 없는 쓰기를 루프가 새로 만들면(예: 체중을 기록했더니 LLM이 일정을 더 만듦) `execute` 없이 확인 카드로 멈춘다. 판정은 지금 동사형 명령 판정(`runs_now`)을 원래 메시지에 대어 본다.
5. 소유 검사·코드 값 검사는 Java가 한다. Python 재검증(`action_card`·`_rejected`)도 그대로.
6. 서비스 범위 밖(`decline`)은 어느 단계에서 골라도 범위 안내로 끝낸다.
7. 같은 쓰기 반복 막기(2026-11-26): 한 턴(이어 가기 포함)에서 같은 도구를 같은 `input`으로 다시 고르면 카드를 만들지 않고 "이미 실행한 일"이라고 LLM에 돌려준다(결과를 잘못 읽은 LLM의 중복 저장 막기). 5절 칸 오류 고치기는 `input`이 달라지므로 해당 없음. 토큰 `cards`에 지난 멈춤의 `tool`·`input`을 남겨 비교한다.

## 7. 평가

`scripts/tool_eval.py`에 다단계 세트를 더한다(②). 가짜 Java 읽기·쓰기 결과(`DONE`·`FAILED`+`errors`)로 루프를 끝까지 돌린다.

| 꼴 | 예 | 정답 |
| --- | --- | --- |
| 쓰기 → 읽기 | "탄이 체중 4.2kg 기록하고 지난주보다 늘었는지 알려 줘" | 체중 카드 → (DONE) → 체중 READ → 비교 글 |
| 읽기 → 조건 쓰기 | "내일 병원 일정 있으면 7시로 바꿔 줘" | 일정 READ → 있으면 수정 카드, 없으면 글 |
| 칸 오류 | 체중 카드 → FAILED `errors: [{field: "hlthVl"}]` | 고친 카드 1번, 두 번째 실패면 글 |
| 단순 명령 | "산책 30분 기록해 줘" | 카드 하나, `pending` 없음(지금과 같음) |
| 하지 말 것 | "체중 기록해 줘"(값 없음) | 되물음에서 멈춤, 다른 쓰기 없음 |

- 지표: 다단계 정답률, 쓰기 잘못(말하지 않은 쓰기·잘못된 번호) 0, 상한 걸림 수, 턴 시간 중앙값.
- 모델은 Haiku 유지. 다단계 정답률 기준(②에서 정함)을 못 넘으면 `--sonnet`으로 비교해 사람이 정한다.
- ③ 쓰기 꼴(2026-11-26, `tests/chat/data/agent_write_eval.jsonl` 6문항, 행의 `results`가 가짜 실행 결과): 읽기 꼴 8문항과 합쳐 Haiku 세 번 잼: 14/14(중앙값 3,451ms)·14/14(4,034ms, 검증)·13/14(3,905ms, A08 "체중 기록해 줘"에 도구 없이 글로 되물음 — ② 읽기 꼴 행, 쓰기 꼴 6문항은 매번 6/6). 쓰기 잘못 0, 상한 걸림 0. 중앙값은 이어 가기 포함 한 문항 전체 시간. 칸 오류 뒤 LLM은 바로 고치지 않고 일지를 한 번 읽은 뒤 고친 카드를 냄(W02·W03).
- ③ 이어 가기 구현: 원래 질문(방의 그 사용자 메시지) 뒤에 "이 턴 진행 기록"(앞 단계 READ 결과 글·실행 결과 줄)을 붙여 도구 고르기를 다시 부른다(`clients.resume`·`with_notes`). 토큰 `messages` 대신 `notes`(글 목록)를 담고, 앞 대화는 방에서 다시 읽는다(`build_context`). 그래서 이어 간 단계도 지금 READ·카드·안전 규칙 경로를 그대로 탄다. 실행한 일이 있으면 앞 READ 결과 줄은 "쓰기 실행 전"으로 표시해 답에 쓰려면 다시 읽게 하고, `pending`을 주는 READ 뒤 카드 턴의 글은 남은 일(비교 등)을 답하지 않고 "등록하고 이어서 알려 드릴게요."로 끝내게 한다(검증 2차, 2026-11-26).

2. `pending`을 언제 줄지: 추천은 "같은 응답에 다른 도구가 없고 단순 명령 하나면 안 줌"(2절). 늘 주면 React가 매번 `agent-continue`를 한 번 더 부른다.
3. 되물음 뒤 이어 가기: 회원이 빈 칸을 채운 다음 메시지에 토큰을 실어 루프를 이어 갈지(`MessageSendRequest.agentToken`). 추천: ③에서는 안 함(새 턴), 써 보고 정한다.
4. 상한 값 도구 8번·토큰 10분: 평가 뒤 조정(3절). 더 높여도 60초 안에 들어오나 맴도는 루프 피해를 줄이려고 8번부터(2026-11-26 사람 결정).
5. `agent-continue`의 사용자 메시지: 저장하지 않는다(사용자 말이 없음). 이어 간 답은 같은 턴의 AI 메시지로 저장한다. 프론트가 결과 글(`action-result`)과 이어 간 답을 차례로 그리는지 합의.
6. 프론트 합의: `step` 표시 문구("○○ 확인 중"), `pending`이 있을 때 결과 저장 뒤 `agent-continue` 호출, 실패해도 결과 글은 남김.
7. 카드가 많을 때 확인 글 길이: 카드 상한을 없애면 "이렇게 할까요?" 번호 줄이 8줄까지 길어져 회원이 다 읽지 않고 확인하거나 빈 칸 안내가 묻힐 수 있다(동사형 명령의 "…할게요" 글도 같음). 후보 ⓐ 같은 도구 카드는 한 줄로 묶기("탄이·코코·루루 체중 기록 — 11-26(목) · 4.2 / 3.8 / 5.1kg") ⓑ N줄이 넘으면 앞 줄만 보이고 "외 N건". ③에서 프론트 카드 표시와 함께 정한다.

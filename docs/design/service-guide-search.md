# 서비스 안내 검색 설계 (초안)

AI 매니저 채팅에서 "○○ 어떻게 해요?" 같은 서비스 사용법 질문에 답하려고, 안내서(`data/guide/*.yaml`)에서 맞는
사용법을 찾아 답변 근거로 쓰는 방식이다. 2026-11-05 구현(SCR-AIM-002 서비스 기능 안내). 기능명세서에 이 기능(사용법
안내)이 아직 없어 FN-AIM-002-02·002-04·004-02에 걸어 두었고, 기능 ID 추가는 DMS 모음으로 미뤘다.

## 0-1. 구현하며 정한 것 (2026-11-05, LJS)

| 항목 | 결정 |
| --- | --- |
| 2단계 | 별도 LLM 호출을 두지 않고 지금 의도 분류 호출에 목차를 붙인다. 분류 출력의 `guide_id` |
| 응답 계약 | `GUIDE`는 Python 안 분류에만 둔다. SSE `intent.kind`는 `SEARCH`, 바로가기는 `done.shortcut` |
| 청크 ID | task마다 `id`를 직접 적는다(위치 번호를 그대로 옮겨 정답표 유지). 새 task는 새 id를 붙이고 기존 id는 바꾸지 않는다 |
| 바로가기 | 첫 청크의 화면이 라우팅 대상이면 그 화면, 아니면 분류의 연관 화면(`related_num`) |
| 분류 캐시 | 켜지 않는다(목차 비용 질문 1만 번에 약 4달러, 기존 테스트가 `system` 문자열 비교). 분류 로그에 입력 토큰 수 |
| 의료 고지 | 명세대로 SEARCH 답변에 붙인다. 사용법 답변에서 뺄지는 DMS 모음 |

## 0. 확정한 것 (2026-11-04, LJS)

| 항목 | 결정 |
| --- | --- |
| 검색 방식 | **M1 키워드 색인 → (못 찾으면) LLM 목차 선택 → (그래도 없으면) 범위 밖 안내** 2단계 |
| 검색 단위 | 안내서의 task 하나 = 청크 하나. ID는 `<num>-<순번>`(공통은 `C-<순번>`) |
| 꺼내는 개수 | 상위 3개(top-3)를 답변 프롬프트에 넣는다 |
| 안 쓰는 것 | 벡터 DB·임베딩은 지금 넣지 않는다(5번 "다시 볼 때") |
| 안내서 위치 | `data/guide/*.yaml` 도메인별 파일 + `common.yaml`. `num`으로 `data/routing.yaml`과 연결 |
| AI가 읽지 않는 것 | 안내서의 `diffs`·`todo`는 사람용. 청크 본문에 넣지 않는다(분리 권장: `docs/guide-review.md`) |

## 1. 흐름

```
사용자 질문
  └─ 의도 판정(judge) ── ROUTE·SEARCH·등록 요청이면 지금 흐름 그대로
        └─ GUIDE(사용법 질문)            ← 새 갈래. ClassifiedKind에 추가
              ├─ 1단계 M1 키워드 색인 → 결과 있음 → 상위 3개
              ├─ 2단계 결과 없음 → LLM에 task 제목 목록을 주고 번호를 고르게 함 → 고른 청크
              └─ 3단계 LLM도 못 고름 → 범위 밖 안내(지금 OUT_OF_SCOPE 문구)
  └─ 답변 생성: 꺼낸 청크(summary·entry·steps·notes)만 근거로 답하게 지시
  └─ 바로가기: 고른 청크의 num이 routable이면 기존 ROUTE와 같은 바로가기 버튼을 붙인다
```

- 색인은 `routing_table()`처럼 서버 시작 때 한 번 만든다(`@lru_cache`).
- 2단계 목록은 task 제목 약 140개다. 제목만이면 2천~3천 토큰으로 어림한다(재지 않음).

## 2. M1 키워드 색인

```python
# 공백 뺀 검색어 → [(청크 ID, 가중치)]
index = {"가족초대": [("27-1", 1.0)], "가계부": [("30-1", 0.3), ("30-2", 0.3), ...], ...}
```

| 검색어 출처 | 가중치 |
| --- | --- |
| task의 `faq_keywords`, task 제목 | 1.0 |
| 화면 이름, 그 num의 routing.yaml `keywords` | 0.3 (화면 전체 task에 붙는다) |

- 공백 제거는 `rules._compact`를 그대로 쓴다. 라우팅과 같은 기준이어야 결과가 어긋나지 않는다.
- 2글자 미만 검색어는 넣지 않는다.
- 점수: 질문(공백 뺀)에 들어 있는 검색어마다 `글자 수 × 가중치`를 더한다. 점수 순 상위 3개, 점수 0이면 결과 없음.
- 기존 `match_route`와 원리가 같다(최장 일치 → 점수 합으로 확장).

## 3. 왜 이 방식인가 — 오프라인 평가 (2026-11-04)

LLM 없이 검색 단계만 비교했다. 질문 50개(사용법 45, 범위 밖 5), 청크 144개.

| 방식 | hit@1 | hit@3 | 범위 밖 거절 | 실패할 때 모양 |
| --- | --- | --- | --- | --- |
| **M1 키워드 색인** | 33% | 56% | **5/5** | 실패 20건 중 **16건이 결과 없음** |
| M2 색인 없이 본문 2-gram(BM25) | 44% | 60% | 1/5 | 항상 무언가를 내놓음 |
| M3 M1+M2 합침 | 47% | 69% | 1/5 | 실패 14건 모두 틀린 결과 |

유형별 hit@3(M1 / M2 / M3): 일상어 8·11·14 /25, 메뉴 이름 직접 10·9·9 /10, 줄임말·오타 7·7·8 /10

판단
- M3가 점수는 가장 높지만 모를 때도 자신 있게 틀린다("고양이가 토해요" → 실종센터). 챗봇이 엉뚱한 화면을 확신 있게
  안내하는 쪽이 "모른다" 후 다음 단계로 넘기는 쪽보다 나쁘다.
- M1은 실패의 80%가 "결과 없음"이라 2단계(LLM)로 넘길 신호가 깨끗하다. 메뉴 이름을 넣은 질문은 10/10.
- 속도는 판단 기준이 아니다(질문당 0.1~0.7ms, LLM 응답 수 초에 묻힌다).

용어
- top-k: 점수 순 상위 k개를 꺼내는 것. 여기서는 k=3
- hit@k: 꺼낸 k개 안에 정답이 하나라도 있었던 질문의 비율

## 4. 이 평가의 한계 (결정 전에 다시 잴 것)

- 질문은 LLM이 IA 구조도만 보고 만들었다(안내서는 안 봄). 실제 사용자 말투보다 쉬울 수 있다.
- 정답표는 한 사람(LLM 보조)이 붙였다. 정답이 여럿인 질문은 판단이 들어갔다.
- 45문항이라 한두 문제에 5%p씩 움직인다. M2·M3 차이는 우연일 수 있다.
- **2단계(LLM 목차 선택)는 재지 않았다.** M1+LLM이 낫다는 것은 1단계 실패 모양에서 나온 추측이다.
- 지금 실패한 질문에 맞춰 키워드를 보강하면 이 세트 점수는 오르지만 의미가 없다(시험지 맞춤). 보강했다면 **새 질문 세트로** 다시 잰다.

## 5. 남은 일

| 할 일 | 비고 |
| --- | --- |
| AI매니저 기능명세서에 사용법 안내 기능 ID 추가 | 명세 먼저(AGENTS.md 흐름) |
| `ClassifiedKind.GUIDE` 추가와 분류 프롬프트 수정 | 지금 질문꼴 입력은 `question_markers`로 AI 분류에 가지만 갈 곳이 없다 |
| `data/guide/*.yaml` 넣기 | 초안은 프론트 세션에서 만든 `service_guide.yaml`(화면 34행, task 138개 + 공통 6개). 도메인별로 나눠 넣는다 |
| 색인·조회 구현 | `app/chat/rules.py` 옆. 평가 스크립트 `run_eval.py`의 M1을 옮기면 된다 |
| 2단계 LLM 목차 선택 구현 | 구조화 출력으로 청크 ID 하나 또는 없음 |
| 테스트 | ① guide의 num이 routing.yaml 라우팅 행과 맞고 중복 없음 ② 청크 ID 유일 ③ 평가 세트 hit@3 하한(회귀 방지) |
| 실제 질문으로 다시 평가 | 대화 로그나 팀원이 쓴 질문 50개. M1 단독과 M1+LLM의 hit@3·답변 정확도·토큰 비교 |
| 안내서 데이터 검사 | 버튼 이름이 프론트 코드에 실제로 있는지, 경로가 실제 라우트인지(초안은 서브에이전트가 썼다) |

다시 볼 때: 실제 질문 평가에서 M1+LLM이 일상어 질문을 많이 놓치면 임베딩 검색을 1단계 뒤에 붙이는 하이브리드를 검토한다.

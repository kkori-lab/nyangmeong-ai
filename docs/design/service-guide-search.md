# 서비스 안내 검색 설계 (초안)

AI 매니저 채팅에서 "○○ 어떻게 해요?" 같은 서비스 사용법 질문에 답하려고, 안내서(`data/guide/*.yaml`)에서 맞는
사용법을 찾아 답변 근거로 쓰는 방식이다. 2026-11-05 구현(SCR-AIM-002 서비스 기능 안내). 기능명세서에 이 기능(사용법
안내)이 아직 없어 FN-AIM-002-02·002-04·004-02에 걸어 두었고, 기능 ID 추가는 DMS 모음으로 미뤘다.

## 0-1. 구현하며 정한 것 (2026-11-05, LJS)

| 항목 | 결정 |
| --- | --- |
| 2단계 | 별도 LLM 호출을 두지 않고 지금 의도 분류 호출에 목차를 붙인다. 분류 출력의 `guide_id` |
| 응답 계약 | `GUIDE`는 Python 안 분류에만 둔다. SSE `intent.kind`는 `SEARCH`, 바로가기는 `done.shortcut` |
| 청크 ID | task마다 `id`를 직접 적는다(위치 번호를 그대로 옮겨 정답표 유지). 새 task는 새 id를 붙이고 기존 id는 바꾸지 않는다 |
| 바로가기 | 첫 청크의 화면이 라우팅 대상이면 그 화면, 아니면 분류의 연관 화면(`related_num`) |
| 분류 캐시 | 켠다(2026-11-05 후속). 규칙·목차 블록에 `cache_control: ephemeral`, 키워드 힌트는 그 뒤 블록. 실측 캐시 읽기 7,501토큰·캐시 밖 입력 약 20토큰. 5분 안에 다음 질문이 없으면 캐시가 사라져 다시 쓴다. 분류 로그에 입력·캐시 읽기·쓰기 토큰 수 |
| 의료 고지 | 명세대로 SEARCH 답변에 붙인다. 사용법 답변에서 뺄지는 DMS 모음 |

## 0. 확정한 것 (2026-11-04, LJS)

| 항목 | 결정 |
| --- | --- |
| 검색 방식 | **M1 키워드 색인 → (못 찾으면) LLM 목차 선택 → (그래도 없으면) 범위 밖 안내** 2단계 |
| 검색 단위 | 안내서의 task 하나 = 청크 하나. ID는 `<num>-<순번>`(공통은 `C-<순번>`) |
| 꺼내는 개수 | 상위 3개(top-3)를 답변 프롬프트에 넣는다 |
| 안 쓰는 것 | 벡터 DB·임베딩은 지금 넣지 않는다(5번 "다시 볼 때") |
| 안내서 위치 | `data/guide/*.yaml` 도메인별 파일 + `common.yaml`. `num`으로 `data/routing.yaml`과 연결 |
| AI가 읽지 않는 것 | 안내서의 `diffs`·`todo`는 사람용. 청크 본문에 넣지 않는다(분리 권장: `docs/guide-review.md`) |

## 1. 흐름

```
사용자 질문
  └─ 의도 판정(judge) ── ROUTE·SEARCH·등록 요청이면 지금 흐름 그대로
        └─ GUIDE(사용법 질문)            ← 새 갈래. ClassifiedKind에 추가
              ├─ 1단계 M1 키워드 색인 → 결과 있음 → 상위 3개
              ├─ 2단계 결과 없음 → LLM에 task 제목 목록을 주고 번호를 고르게 함 → 고른 청크
              └─ 3단계 LLM도 못 고름 → 범위 밖 안내(지금 OUT_OF_SCOPE 문구)
  └─ 답변 생성: 꺼낸 청크(summary·entry·steps·notes)만 근거로 답하게 지시
  └─ 바로가기: 고른 청크의 num이 routable이면 기존 ROUTE와 같은 바로가기 버튼을 붙인다
```

- 색인은 `routing_table()`처럼 서버 시작 때 한 번 만든다(`@lru_cache`).
- 2단계 목록은 task 제목 약 140개다. 제목만이면 2천~3천 토큰으로 어림한다(재지 않음).

## 2. M1 키워드 색인

```python
# 공백 뺀 검색어 → [(청크 ID, 가중치)]
index = {"가족초대": [("27-1", 1.0)], "가계부": [("30-1", 0.3), ("30-2", 0.3), ...], ...}
```

| 검색어 출처 | 가중치 |
| --- | --- |
| task의 `faq_keywords`, task 제목 | 1.0 |
| 화면 이름, 그 num의 routing.yaml `keywords` | 0.3 (화면 전체 task에 붙는다) |

- 공백 제거는 `rules._compact`를 그대로 쓴다. 라우팅과 같은 기준이어야 결과가 어긋나지 않는다.
- 2글자 미만 검색어는 넣지 않는다.
- 점수: 질문(공백 뺀)에 들어 있는 검색어마다 `글자 수 × 가중치`를 더한다. 점수 순 상위 3개, 점수 0이면 결과 없음.
- 기존 `match_route`와 원리가 같다(최장 일치 → 점수 합으로 확장).

## 3. 왜 이 방식인가 — 오프라인 평가 (2026-11-04)

LLM 없이 검색 단계만 비교했다. 질문 50개(사용법 45, 범위 밖 5), 청크 144개.

| 방식 | hit@1 | hit@3 | 범위 밖 거절 | 실패할 때 모양 |
| --- | --- | --- | --- | --- |
| **M1 키워드 색인** | 33% | 56% | **5/5** | 실패 20건 중 **16건이 결과 없음** |
| M2 색인 없이 본문 2-gram(BM25) | 44% | 60% | 1/5 | 항상 무언가를 내놓음 |
| M3 M1+M2 합침 | 47% | 69% | 1/5 | 실패 14건 모두 틀린 결과 |

유형별 hit@3(M1 / M2 / M3): 일상어 8·11·14 /25, 메뉴 이름 직접 10·9·9 /10, 줄임말·오타 7·7·8 /10

판단
- M3가 점수는 가장 높지만 모를 때도 자신 있게 틀린다("고양이가 토해요" → 실종센터). 챗봇이 엉뚱한 화면을 확신 있게
  안내하는 쪽이 "모른다" 후 다음 단계로 넘기는 쪽보다 나쁘다.
- M1은 실패의 80%가 "결과 없음"이라 2단계(LLM)로 넘길 신호가 깨끗하다. 메뉴 이름을 넣은 질문은 10/10.
- 속도는 판단 기준이 아니다(질문당 0.1~0.7ms, LLM 응답 수 초에 묻힌다).

용어
- top-k: 점수 순 상위 k개를 꺼내는 것. 여기서는 k=3
- hit@k: 꺼낸 k개 안에 정답이 하나라도 있었던 질문의 비율

## 4. 이 평가의 한계 (결정 전에 다시 잴 것)

- 질문은 LLM이 IA 구조도만 보고 만들었다(안내서는 안 봄). 실제 사용자 말투보다 쉬울 수 있다.
- 정답표는 한 사람(LLM 보조)이 붙였다. 정답이 여럿인 질문은 판단이 들어갔다.
- 45문항이라 한두 문제에 5%p씩 움직인다. M2·M3 차이는 우연일 수 있다.
- **2단계(LLM 목차 선택)는 재지 않았다.** M1+LLM이 낫다는 것은 1단계 실패 모양에서 나온 추측이다. → 4-1절에서 쟀다.
- 지금 실패한 질문에 맞춰 키워드를 보강하면 이 세트 점수는 오르지만 의미가 없다(시험지 맞춤). 보강했다면 **새 질문 세트로** 다시 잰다.

## 4-1. 재평가 (2026-11-05, 프론트 대조 반영 뒤)

`uv run python -m scripts.guide_eval [세트]`로 잰다(실제 Anthropic 호출). M1+LLM은 실제 판정 흐름 `service.judge` 그대로다(룰 라우팅 → 분류 LLM → GUIDE면 M1, 없으면 목차 선택). 답변 본문은 `.cache/guide_eval/`에 남는다(git 제외).

새 세트 `tests/chat/data/guide_eval2.jsonl`(50문항)은 안내서·옛 세트·키워드를 보지 않은 별도 에이전트가 DMS 화면설계서의 화면명·기능 설명만 보고 썼다. 정답표 `guide_labels2.json`은 사람(LLM 보조) 한 명이 안내서를 보고 붙였다. R18(비밀번호 찾기)은 로그인 화면이 안내서 밖이라 `null`로 두고 집계에서 뺐다.

| 세트 | 사용법 문항 | M1 hit@3 | M1+LLM hit@3 | M1+LLM hit@1 | 맞는 화면으로 이동(ROUTE) | 범위 밖 거절 |
| --- | --- | --- | --- | --- | --- | --- |
| 새 세트 | 44 | 21 | 22~24 | 20~22 | 14/14 | 5/5 |
| 옛 세트 | 45 | 25 | 26~29 | 20~23 | — | 5/5 |

- 범위는 같은 세트를 2~3번 돌린 값이다. LLM 분류가 매번 조금씩 달라 2~3문항씩 움직인다.
- 새 세트 유형별 M1+LLM hit@3: 일상어 9~11/24, 직접 9~10/10, 대충 2~3/10. 대충 유형이 낮은 것은 대부분 화면 이동(ROUTE)으로 처리돼서다.
- **사용법 문항 14개는 안내서 답변 대신 화면 이동이 된다**(룰 라우팅이나 분류 ROUTE). 14개 모두 정답 청크의 화면으로 갔다. "가계부 어디서 봐"를 가계부로 보내는 것은 틀린 답이 아니다. hit@3에 이동을 더하면 새 세트는 38/44다.
- 안내서도 이동도 못 한 문항은 6개다.
  - R03 영수증 자동 입력, R08 이메일 변경, R19 모자 사기: M1이 엉뚱한 청크(병원 찾기·마이페이지 홈·캐릭터 만들기)를 잡았다. M1에 결과가 있으면 목차 선택을 쓰지 않아서, 분류 LLM이 맞는 번호를 골랐더라도 버려진다.
  - R13 "다른 집사들 사료 물어볼 데": 분류가 SEARCH(반려동물 지식)로 봤다.
  - R15 "누가 뭐 보낸 것 같은데": 목차 선택이 채팅(10-1)을 골랐다(정답은 알림 C-3).
  - R38 "가게부 어디서봐여": 오타라 FALLBACK이 됐다.
- R23·R44(공동양육)는 SCR-MYP-004로 이동한다. 프론트에서 그 경로가 빈 화면이다(`docs/guide-review.md` "프론트 대조" A).
- 토큰(문항당 평균): 분류는 캐시 읽기 7,501 + 캐시 밖 입력 약 140 + 출력 약 180, 답변은 입력 약 1,700 + 출력 약 380.
- 답변 정확도(2026-11-05 사람 채점, 1207 실행의 답변 27개): 맞음 24 · 부분 1 · 틀림 2. 답변이 없는 문항(화면 이동·범위 밖·SEARCH)은 답변을 만들지 않아 채점에서 뺐다.
  - 틀림 R03(영수증 자동 입력)·R08(이메일 변경): 둘 다 M1이 엉뚱한 청크를 잡은 문항이다. R03의 정답은 "대화창에 영수증 사진을 올리면 인식해 등록"인데 안내서에 그 task가 없다(건강 일지 진입 경로에 한 줄만 있음).
  - 부분 R35(대화창 전체 화면): 새 창으로 열린다는 안내는 맞지만 "전체 화면 기능이 없다"고 단정했다.
  - 청크가 맞으면 답변은 거의 맞는다. 정확도를 올리려면 청크 고르기(M1이 목차 선택을 덮는 문제)와 안내서 빈칸부터 고친다.

판단: 놓친 문항이 6/44이고 일상어에 몰리지 않아 임베딩 하이브리드는 아직 붙이지 않는다. 먼저 고칠 후보는 "M1 결과와 목차 선택이 다르면 목차 선택을 앞에 붙이기"다(R03·R08·R19). 고치면 세트 3번째를 만들어 다시 잰다.

## 4-2. 목차 선택 우선 뒤 재평가 (2026-11-05 15:30, 1회)

4-1절의 판단대로 고쳤다. 분류 LLM이 목차에서 고른 청크를 맨 앞에 두고, M1 결과를 중복 없이 뒤에 붙인다(최대 3개, `rules.merge_guide`).
도구 흐름의 `search_guide`도 같은 함수를 쓴다. 안내서에 `C-7` "AI 대화창에서 영수증 사진으로 검진기록 등록하기"를 더했고,
정답표 R03·R39에 `C-7`을 더했다(둘 다 영수증 사진을 올려 등록하는 법을 묻는 질문, R39는 평가 뒤 사람이 정함). 세 번째 세트는 만들지 않았다. 도구 흐름 비교는
`tool_eval.jsonl`이 맡는다(`tool-calling.md` 7-1절).

| 세트 | 사용법 문항 | M1 hit@3 | M1+LLM hit@3 | M1+LLM hit@1 | 맞는 화면으로 이동(ROUTE) | 범위 밖 거절 |
| --- | --- | --- | --- | --- | --- | --- |
| 새 세트(4-1절, 고치기 전) | 44 | 21 | 22~24 | 20~22 | 14/14 | 5/5 |
| 새 세트(고친 뒤) | 44 | 21 | 25 | 24 | 15/15 | 5/5 |

- **R03·R08·R19 모두 맞혔다.** M1은 그대로 엉뚱한 청크(2-1·5-1·6-1)를 잡았지만, 목차 선택(C-7·32-1·28-2)이 맨 앞에 왔다.
  R38 "가게부 어디서봐여"도 이번에는 목차 선택(30-6)으로 맞혔다(4-1절에서는 FALLBACK).
- **새로 놓친 문항은 R36이다.** M1 결과가 없어 이번 수정과는 관계없다.
  - R36 "알림끄는거 어딧음": 목차 선택이 C-3(알림 확인)을 골랐다(4-1절에서는 9-1로 맞음). LLM이 실행마다 다르게 고르는 범위다.
  - R39 "영수증올리는거 되나요??": 목차 선택이 새 `C-7`을 골랐다. 정답표가 14-2·30-2(건강 일지·가계부 영수증)뿐이라 처음에는 틀림으로 셌다.
    대화창 영수증 등록도 맞는 답이라 사람이 정답표에 `C-7`을 더했고, 표의 값은 더한 뒤로 다시 센 것이다(더하기 전 hit@3 24·hit@1 23).
- 그대로 놓친 문항: R13(SEARCH로 분류), R15(10-1 채팅을 고름), R24(FALLBACK). R18은 집계 제외.
- 사용법 문항 단계: 목차 선택이 들어간 것 18, M1만 9, 이동 15, SEARCH 1, FALLBACK 1.
- 토큰(문항당 평균): 분류 캐시 읽기 7,538 + 캐시 밖 입력 143 + 출력 163, 답변 입력 1,706 + 출력 409. 안내서 목차에 C-7 한 줄이 늘어 캐시 읽기가 37토큰 늘었다.
- 답변 정확도는 이번에 사람이 채점하지 않았다(답변 본문은 `.cache/guide_eval/guide_eval2-20261105-1530.md`).

판단: hit@1이 20~22에서 24로 올랐고, 목차 선택을 버려서 틀리던 3문항이 풀렸다. 한 번만 돌렸으므로 hit@3 25는 4-1절보다 한 문항 위로 본다(R39 정답표 변경분 포함).

| 실제 질문으로 다시 평가 | 2026-11-05 새 세트로 1회(4-1절). 실제 대화 로그·팀원 질문으로는 아직 |
| 안내서 데이터 검사 | 2026-11-05 프론트 develop de4b256과 대조해 32곳 고침(`docs/guide-review.md` "프론트 대조") |

다시 볼 때: 실제 질문 평가에서 M1+LLM이 일상어 질문을 많이 놓치면 임베딩 검색을 1단계 뒤에 붙이는 하이브리드를 검토한다.
